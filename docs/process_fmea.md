# 공정 FMEA 1차 운영 안내

## 범위와 입력

- 표준문서 관리 → 공정 FMEA에서 신규 등록, 초안 저장, 현재 사용 적용, 개정 등록, 폐기, 인쇄를 제공합니다.
- genesis03/FMEA의 기본정보 및 분석표를 활용하되 MES의 FastAPI/Jinja2/SQLAlchemy에 맞게 구현합니다. React/Flask 앱이나 별도 fmea.db는 복사하지 않습니다.
- 대상은 공정 FMEA(PFMEA)입니다. 예방/검출 항목은 현 공정관리로 표시합니다.
- 품목은 기존 item_master의 item_id에 연결하며 품번/품명은 마스터 표시값입니다. 회사명은 임의 기본값 없이 직접 입력하고 작성자/부서는 로그인 사용자 정보를 기본 표시합니다.
- FMEA 번호는 직접 입력하며 같은 품목 내 중복 번호는 차단합니다. 번호를 바꾸어 별도 문서로 신규 등록할 수 있으나 기존 문서를 덮어쓰지 않습니다.
- 분석행의 공정은 기존 processes 마스터를 사용하며 한 문서에 여러 공정을 작성할 수 있습니다.
- S/O/D는 참고 양식의 1~10 범위이며 미평가를 1로 자동 채우지 않습니다. RPN은 서버와 화면에서 계산합니다. 위험 기준, 색상 임계값, AP 판정은 임의로 추가하지 않았습니다.
- 조치 전/후 RPN, 원인, 공정관리 예방/검출, 권고 조치, 담당자/목표일, 조치 내용/완료일을 제공합니다.
- 초안은 미완성 분석을 저장할 수 있습니다. 현재 사용 적용은 최소 1개 행, 활성 공정, 기능/고장 형태/영향/원인, 조치 전 S/O/D 평가가 필요합니다. 조치 후 평가를 시작했으면 세 점수를 모두 입력합니다.
- 분석행은 문서당 최대 500개이며 입력 길이/점수/날짜/행 ID를 서버에서도 검증합니다.
- 인쇄는 저장된 해당 개정의 조회 전용 화면에서 진행하며 A3 가로 방향을 권장합니다. 브라우저의 PDF 저장을 사용할 수 있습니다.

## 개정 및 이력

- fmea_documents: 영구 item_id, FMEA 번호, 등록자/등록일.
- fmea_revisions: 독립 개정번호/순서/상태, 이전 개정, 기준 도면 Revision, 기본정보/당시 품번·품명, 적용/폐기 정보, 낙관적 동시 수정 방지 version.
- fmea_rows: 개정별 공정 참조 및 당시 코드/명칭 스냅샷, 분석 내용/점수/조치/날짜, 초안 행 제외 이력.
- FMEA 개정번호는 도면 Revision과 별개입니다. 선택한 동일 품목 도면 Revision을 기준으로 연결할 수 있지만 도면의 현재 사용/품목마스터 Revision은 변경하지 않습니다.
- 현재 사용 적용 시 같은 FMEA 문서의 기존 현재 사용본은 구버전으로 전환합니다. 문서당 현재 사용본은 최대 1개이며 DB 고유 인덱스로 보호합니다.
- 적용된 개정은 내용 수정/행 제외를 허용하지 않습니다. 현재 사용 또는 구버전에서 새 번호·개정 사유로 개정 등록하면 기존 분석표를 복사한 초안이 생성됩니다. 한 문서에 작성 중 초안이 있으면 새 초안을 중복 생성하지 않습니다.
- 초안에서 저장된 행을 제외해도 물리 삭제하지 않고 retired_at/retired_by_id를 기록합니다. 적용/구버전/폐기 분석표와 원본 행은 보존합니다.
- 폐기는 사유 필수이며 구버전을 자동으로 현재 사용에 재적용하지 않습니다.
- 기존 품목/공정 삭제 API는 FMEA 이력(폐기 포함)이 있으면 삭제를 차단합니다. 사용중지로 처리합니다.
- 기존 최고관리자 공정코드 변경은 process_code 참조를 일괄 변경하는 구조를 재사용합니다. FMEA 당시 공정 코드/명칭 스냅샷은 그대로 남아 인쇄 이력을 보존합니다.
- 품목 변경 시 현재 화면의 품번/품명은 최신 마스터를 표시하고, 적용된 FMEA의 당시 품번/품명 스냅샷은 보존합니다.
- 저장/개정/적용/폐기는 품목 잠금과 version 검사로 동시 변경을 차단하고 기존 감사로그를 재사용합니다.
- 현재 사용 적용은 별도 결재/승인 워크플로우가 아닙니다. 등록자/작성자/적용자는 구분하여 기록합니다.

## 권한과 제외 범위

- 기존 사이드바 자동 생성 권한의 /standard-documents/process-fmea를 사용합니다. READ는 조회/인쇄, WRITE는 등록/수정/적용/개정/폐기입니다. 화면뿐 아니라 API에서도 직접 검사합니다.
- 기존 일반 계정에는 권한을 자동 부여하지 않습니다.
- 별도 승인 결재, AP 평가, CP 자동 생성/연결, FMEA 첨부파일 업로드, 생산시점 FMEA 적용 이력은 이번 범위에 포함하지 않습니다.
- 기존 도면 관리와 LOT·생산·검사 이력은 변경하지 않습니다.

## 검사기준서 메뉴 통합

- 표준문서 관리 → 검사기준서 관리 아래에 입고검사 기준서 / 검사항목 마스터 두 탭을 둡니다.
- 품질관리의 기존 두 사이드바 링크만 제거하며 기존 테이블, 검사 내용, 작성/조회 URL 및 API는 재사용합니다. 데이터 이동/삭제는 하지 않습니다.
- 통합 진입 경로 /standard-documents/inspection-standards는 읽기 권한이 있는 기존 탭으로 이동합니다.
- 기존 /quality/inbound-standards와 /quality/inspection-items의 권한을 그대로 사용합니다. 하나의 탭만 허용된 계정은 해당 탭만 표시합니다.
- 사용자 관리에서는 표준문서 관리 그룹 아래 두 탭의 READ/WRITE를 따로 설정합니다. 이동 전 저장된 메뉴별 권한 키를 변경하거나 자동 확대하지 않습니다.
- 기준서 조회/편집에 필요한 검사항목 목록 조회는 기준서 읽기 권한으로 허용하지만 검사항목 마스터 쓰기 권한은 부여하지 않습니다.
- 각 검사 API는 해당 탭의 권한을 직접 검사하여 화면 이동이 읽기 전용 권한을 우회하지 않게 합니다.
- 공정/출고 검사기준서 확장과 성적서 자동 연결, 기존 기준서의 수정/삭제/개정 정책 개선은 다음 별도 설계 대상입니다. 이번에는 기존 기능을 유지합니다.

## 업데이트 및 배포

- 사용자가 GitHub main에서 git pull한 뒤 MES 서버를 재시작합니다. 기존 모델 등록/create_all 방식으로 FMEA의 신규 3개 테이블/인덱스가 생성됩니다. 기존 테이블 구조는 바꾸지 않습니다.
- 실제 로컬 검증은 사용자가 수행합니다. 이번 구현에서는 실행 테스트나 브라우저 점검을 수행하지 않았습니다.
- GitHub의 manual_labels.db, 업로드 파일 원본, Oracle 운영 DB는 수정하지 않았습니다. Oracle Cloud 배포는 하지 않습니다.
- 이후 Oracle 일괄 배포 전 실제 운영 DB와 문서 원본을 함께 백업합니다. /home/ubuntu/MES/data/manual_labels.db를 GitHub DB로 덮어쓰지 않습니다.
