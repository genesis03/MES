# 도면 관리 1차 운영 안내

## 화면과 등록 순서

- 기초 정보 → 도면 관리에서 전체 품목을 검색합니다. 이전 품번도 검색할 수 있습니다.
- 품목 정보 관리에서 저장된 품목을 선택하고 **도면 조회**로 이동할 수 있습니다.
- 최초 등록 → 품목 Revision 입력 → 초안 생성 → 도면 제목/도면번호/문서 표기 Revision/파일/비고 입력 → 도면 초안 저장.
- 도면 확인 후 **현재 사용 적용**을 실행합니다. 초안 저장만으로 기존 사용 도면이 바뀌지 않습니다.
- 개정할 때 이전 Revision을 선택하여 **개정 등록**을 실행하고 새 Revision, 개정 사유, 이번 개정에 사용할 파일을 등록합니다.
- 새 Revision 적용 시 기존 현재 Revision을 구버전으로 전환합니다. 품목당 현재 사용 Revision은 최대 1개이며 DB 고유 인덱스로도 보호합니다.
- 초안에는 여러 도면을 등록할 수 있고, 한 도면에 PDF/이미지와 CAD 원본을 함께 첨부할 수 있습니다. 기존 파일이 자동 복사되는 기능은 1차에 포함하지 않습니다.
- 적용된 Revision에 파일을 추가/교체하지 않습니다. 새 개정을 등록합니다.
- 초안의 잘못 등록한 문서는 사유를 남겨 폐기하고 다시 등록합니다. 원본은 계속 보존됩니다.
- Revision 폐기도 사유를 기록하고 이력/파일을 유지합니다. 현재 Revision을 폐기하면 현재 사용 도면은 없는 상태가 되며 구버전을 자동 재적용하지 않습니다.
- 폐기/구버전도 읽기 권한이 있으면 조회·다운로드할 수 있습니다.

## 품목/기존 기준정보 연결

- 연결은 `item_revisions.item_id → item_master.id`, `item_documents.revision_id → item_revisions.id`, `document_files.document_id → item_documents.id`입니다.
- 품번 변경 시 도면 연결과 저장 경로가 유지됩니다. 품목 정보 화면은 현재 품번을 표시합니다.
- 문서 이력이 있는 품목은 삭제할 수 없습니다. 품목을 사용중지하면 신규 등록/적용은 차단하고 기존 이력 조회/폐기는 허용합니다.
- 도면 이력이 생긴 품목의 Revision은 품목마스터에서 직접 변경할 수 없습니다. 현재 사용 적용 시 품목마스터 표시값을 함께 갱신합니다. 현재 Revision 폐기 시 마지막 적용 표시값은 보존하되 화면에서 현재 사용 없음으로 구분합니다.
- 기존 사용자와 `audit_logs`를 재사용합니다. 등록/적용/구버전 전환/폐기의 변경 이력이 기록됩니다. 다운로드 이력 자체는 1차 범위에 포함하지 않습니다.
- 문서 종류는 `DOCUMENT_TYPE`, 파일 역할은 `DOCUMENT_FILE_ROLE` 공통코드를 사용합니다. 기존 코드를 덮어쓰지 않고 누락된 초기 코드만 추가합니다.
- 1차 화면은 도면에 집중합니다. 테이블은 작업표준서·검사기준서·기타 기술문서로 확장할 수 있습니다.
- 기존 품질관리의 입고검사 기준서와 검사 결과는 변경하지 않습니다. 추후 Revision 연결 정책을 정한 뒤 연동합니다. 과거 LOT에 현재 도면을 임의로 소급 연결하지 않습니다.

## 권한

관리자 사용자 관리의 기초 정보 그룹에 **도면 관리** 메뉴가 자동으로 추가됩니다.

- NONE: 화면/API/미리보기/다운로드 접근 불가.
- READ: 조회/미리보기/다운로드 가능, 생성/업로드/적용/폐기 불가.
- WRITE: 등록/적용/폐기 가능.
- 메뉴별 권한을 사용하는 기존 일반 계정에는 새 메뉴 권한을 관리자가 부여해야 합니다. 기존 권한을 자동 확대하지 않습니다.
- 구형 메뉴별 권한이 없는 계정은 기존 `basic_info` READ/WRITE 판정 구조를 사용합니다.
- 서버는 도면 메뉴 권한을 직접 확인하며 요청 헤더/품목관리 버튼만으로 쓰기 권한을 얻을 수 없습니다.

## 파일 보관과 지원 형식

기본 로컬 저장 위치는 `data/documents`입니다. 환경변수로 설정합니다.

| 설정 | 기본값 |
|---|---|
| DOCUMENT_STORAGE_ROOT | 로컬: 저장소/data/documents, Oracle 컨테이너: /data/documents |
| DOCUMENT_MAX_FILE_BYTES | 52428800 (파일당 50MB) |
| DOCUMENT_MAX_FILES | 도면 1건당 최대 10개 |
| DOCUMENT_ALLOWED_EXTENSIONS | pdf,png,jpg,jpeg,tif,tiff,bmp,dwg,dxf,step,stp,igs,iges |

- 저장 경로: `{item_id}/{revision_id}/{document_id}/{UUID}.{확장자}`. DB에는 상대경로와 원본 파일명/MIME/크기/SHA-256을 저장합니다.
- PDF/이미지는 파일 파서로 형식을 검사합니다. 암호화 PDF는 1차에 지원하지 않습니다.
- CAD는 확장자와 형식 헤더를 검사하고 원본을 보관합니다. CAD 설계 내용의 유효성 검사나 변환/웹 미리보기는 지원하지 않습니다.
- PDF/PNG/JPEG/BMP는 **새 탭에서 보기**로 확인하며 TIFF/CAD는 다운로드하여 확인합니다. 팝업 미리보기는 사용하지 않습니다.
- 새 탭은 브라우저 기본 PDF/이미지 뷰어를 사용합니다. 브라우저에서 PDF를 항상 다운로드하도록 설정한 경우 파일이 다운로드될 수 있습니다.
- 새 탭 링크는 원래 화면과의 연결을 차단하고(`noopener noreferrer`), 미리보기 응답은 다른 페이지에 삽입할 수 없도록 제한합니다. Chrome PDF 뷰어를 차단하는 CSP sandbox는 미리보기 응답에 적용하지 않습니다.
- 파일은 공개 static 폴더 밖에 보관하며 ID 기반 권한 검사 후 응답합니다. 적용/다운로드 때 크기/체크섬을 확인합니다.
- 이력에 등록된 파일은 물리 삭제하지 않습니다. 실패한 업로드 요청에서 새로 만든 미등록 파일만 정리합니다.
- 파일이 없거나 체크섬이 다르면 적용/다운로드를 차단합니다. 파일을 임의 교체하지 말고 해당 백업에서 원본을 복구해야 합니다.
- 서버의 업로드 파일 악성코드 검사와 외부 백업 저장소 연결은 향후 운영 환경에 맞춰 추가할 수 있습니다.

## 로컬 업데이트와 검증

기존 변경 상태를 확인한 뒤 main에서 `git pull --ff-only`를 실행하고, 사용 중인 Python 환경에서 `pip install -r requirements.txt`로 PDF/이미지 검사 의존성을 설치합니다. 현재 서버가 실행 중이면 재시작합니다.

앱 시작 시 기존 자동 초기화 구조에서 새 테이블과 누락 공통코드가 추가됩니다. 기존 DB 파일 자체를 바꾸어 배포하지 않습니다. 업데이트 전 운영 DB 백업을 확보합니다.

개발 검증: `python -m pytest tests/test_documents.py -q` (테스트용 pytest 별도 필요). 테스트는 임시 DB와 임시 문서 폴더를 사용합니다.

## Oracle 배포 시 적용할 사항

이번 구현 단계에서 Oracle 서버에 배포하지 않습니다. 로컬 검증 완료 후 일괄 배포합니다.

- 운영 DB: `/home/ubuntu/MES/data/manual_labels.db`. GitHub의 `manual_labels.db`로 덮어쓰지 않습니다.
- 운영 문서: `/home/ubuntu/MES/data/documents`. 기존 `./data:/data` 영구 볼륨을 사용합니다.
- 컨테이너의 `DOCUMENT_STORAGE_ROOT`는 `/data/documents`로 지정합니다. `.env` 설정이 있으면 compose 환경변수 치환에 우선합니다.
- `data/`와 문서 원본은 Git 추적에서 제외합니다. 재배포 시 문서 폴더를 지우지 않습니다.
- SQLite 실제 DB에는 추가된 테이블과 인덱스만 반영합니다. 코드 저장소의 DB 파일은 배포 대상이 아닙니다.

### DB와 원본을 함께 백업

```bash
docker compose -f docker-compose.oracle.yml exec -T mes \
  python deploy/oracle/backup_db.py \
  --source /data/manual_labels.db \
  --documents-root /data/documents \
  --backup-dir /data/backup \
  --retention-days 14
```

결과 ZIP은 DB 스냅샷, 해당 스냅샷에 등록된 모든 파일(구버전/폐기 포함), 크기/SHA-256 목록을 담습니다. 등록된 원본이 불변이고 삭제되지 않으므로 새 업로드 중에도 스냅샷에 포함된 파일 집합을 보존할 수 있습니다. 원본이 누락/변조된 경우 실패하며 불완전 ZIP을 완료된 백업으로 남기지 않습니다.

기존 `--documents-root` 없는 호출은 DB-only 백업을 유지합니다. `mes-backup.service`에는 통합 ZIP 옵션을 추가했습니다. 일괄 배포 때 서버의 service 파일도 갱신하고 daemon-reload 후 실제 백업 성공을 확인해야 합니다. 매일 03:00 Asia/Seoul, 14일 보관 설정은 유지합니다.

백업 ZIP을 별도 서버/외부 백업 저장소에도 복사해야 서버 전체 장애에 대비할 수 있습니다. 외부 저장소 연결은 아직 수행하지 않았습니다. 문서 원본은 장기 보존하며, 14일은 백업 스냅샷의 보관 기간입니다.

복구 시 MES 쓰기를 중지하고 기존 DB/문서 폴더를 먼저 별도 보존한 후, 같은 ZIP의 `manual_labels.db`와 `documents/`를 함께 복원합니다. `manifest.json`의 파일 크기/체크섬과 DB integrity_check를 확인한 뒤 서버를 다시 시작합니다. GitHub DB를 복구 원본으로 사용하지 않습니다.
