# 표준문서 관리 구성 및 개발 결정

## 이번 반영 범위

기초 정보 바로 다음에 최상위 **표준문서 관리**를 배치하고 전체 메뉴를 먼저 표시합니다.

| 메뉴명 | 경로 | 현재 상태 |
|---|---|---|
| 도면 관리 | /basic-info/drawings | 기존 도면 관리 화면 |
| 공정흐름도 | /standard-documents/process-flows | 품목별 공정번호·명칭·순서·개정·인쇄 |
| 관리계획서 | /standard-documents/control-plans | 상단·관리항목 작성/저장·개정·엑셀 불러오기 |
| 공정 FMEA | /standard-documents/process-fmea | 작성·저장·개정·조회·인쇄 |
| 작업표준서 관리 | /standard-documents/work-standards | 개발 예정 안내 |
| 검사기준서 관리 | /standard-documents/inspection-standards | 입고검사 기준서 / 검사항목 마스터 두 탭 |
| 포장사양서 관리 | /standard-documents/packaging-specifications | 개발 예정 안내 |

- 도면은 사이드바 위치만 이동합니다. 기존 URL, item_id 연결, 파일 보관, Revision 정책, 생산실적/품목관리의 도면 보기 연결은 그대로 유지합니다.
- 작업표준서/포장사양서의 미구현 메뉴는 공통 안내 템플릿 `templates/standard_documents/planned.html`을 사용합니다. 공정 FMEA는 독립 작성 화면을 제공하며 검사기준서는 기존 화면의 탭 구성을 사용합니다.
- 관리자 사용자 관리의 권한 트리는 기존 사이드바 자동 생성 방식을 그대로 사용합니다. 새 그룹 키는 `standard_documents`입니다.
- 도면의 기존 메뉴별 권한 키 `/basic-info/drawings`를 유지합니다. 구형 계정의 기초정보 권한도 도면에 한해 기존 판정/권한 편집 방식을 유지합니다.
- 새 메뉴는 일반 계정에 자동 허용하지 않습니다. 관리자에게는 전체 메뉴가 표시되며, 일반 계정에는 개별 READ/WRITE 권한을 부여한 메뉴만 표시됩니다. 안내 화면도 서버에서 권한을 확인합니다.
- 기존 입고검사 기준서와 검사항목 마스터는 표준문서 관리의 검사기준서 관리 두 탭으로 모읍니다. 기존 URL/API/데이터와 각 탭의 권한 키는 유지하며 품질관리 사이드바에서 두 링크만 제거합니다.

## 이전 대화에서 확정한 방향

### 공정 FMEA

- 명칭과 개발 대상은 **공정 FMEA(PFMEA)**입니다. 설계 FMEA로 구현하지 않습니다.
- 참고 양식: https://github.com/genesis03/FMEA/blob/main/src/components/FMEAForm.tsx
- 기본 정보 양식: https://github.com/genesis03/FMEA/blob/main/src/components/FMEAHeader.tsx
- 기존 양식의 고장 형태, 영향, S/O/D, 원인, 예방·검출 관리, RPN, 권고 조치, 담당자/목표일, 조치 결과/완료일, 조치 후 S/O/D·RPN을 출발점으로 합니다.
- 공정흐름과 공정흐름도는 별도 기능으로 분리하지 않습니다. 공정흐름도에서 직접 입력한 번호·명칭·순서를 FMEA가 참조하며 향후 CP도 같은 기준을 사용합니다. 관리계획서도 같은 공정 순서를 사용합니다.
- 기존 양식에 설계관리 표현이 있더라도 MES에서는 공정 FMEA에 맞게 용어와 품목/공정 연결을 설계합니다. 제공된 양식만으로 특정 최신 FMEA 규격 준수를 주장하지 않습니다.
- React/Flask 애플리케이션이나 별도 fmea.db를 MES에 복사하지 않습니다. FastAPI/Jinja2/SQLAlchemy 구조와 기존 품목·공정·사용자 마스터를 사용합니다.
- 품목은 item_id로 연결하고 part_no는 표시용입니다. 승인된 1차 작성 화면·DB·개정 정책은 docs/process_fmea.md에 기록합니다.

### 문서와 검사 결과 구분

- 도면, CP, 공정 FMEA, 작업표준서, 검사기준서, 포장사양서는 표준문서 관리에서 다룹니다.
- 입고성적서, 공정순회검사, 출고성적서는 품질관리에서 다룹니다. 이번 메뉴 변경에 성적서 기능은 포함하지 않습니다.
- 성적서는 검사기준서의 검사항목과 규격을 가져오고 측정값 외 추가 입력을 최소화합니다.
- 기준 Revision 및 당시 규격의 스냅샷을 보존하여 이후 기준 개정이 과거 검사 결과를 바꾸지 않게 설계합니다.
- 기존 검사항목 마스터와 입고검사 기준을 재사용할 수 있는 범위를 먼저 확인합니다. 입고 기준을 모든 검사 유형에 임의 적용하지 않습니다.

## 완제품 전용 품목 정책

- 공정흐름도, 관리계획서(CP), 공정 FMEA, 포장사양서는 완제품 품목만 선택합니다.
- 품목마스터 material_type과 기존 MATERIAL_TYPE 공통코드 FINISHED(완제품)를 사용합니다. 품번 문자열이나 계정유형으로 추정하지 않습니다.
- 현재 구현된 공정흐름도/FMEA 선택 목록은 사용 중인 완제품만 반환하며 등록·수정·개정·적용 API도 같은 조건을 검사합니다.
- 품목 분류 변경/사용중지 또는 기존 비완제품 문서는 삭제하지 않습니다. 목록·내용·인쇄 이력을 유지하고 조회 전용으로 표시하며 사유를 남기는 폐기는 허용합니다.
- 관리계획서의 작성·수정·적용과 엑셀 검증도 services/standard_document_item_service.py의 완제품 조건을 재사용합니다. 사용 중지된 품목의 기존 문서는 조회만 가능합니다. 포장사양서는 개발 예정 화면입니다.
- 도면 관리, 작업표준서 및 검사기준서의 품목 범위는 이번에 변경하지 않습니다.
- 메뉴명만 CP 관리에서 관리계획서로 변경합니다. 기존 /standard-documents/control-plans 경로/권한 키는 유지합니다.

## 공통 원칙과 적용

- 문서 원본, 구버전, LOT 및 생산/검사 이력을 삭제하지 않습니다.
- Revision/현재 사용 정책과 파일 저장·권한 처리는 공통 기능을 재사용하되 문서별 적용 관계는 다음 설계에서 확정합니다.
- GitHub main 직접 반영 후 사용자가 git pull하고 서버를 재시작하여 메뉴를 확인합니다.
- 요청에 따라 이번 변경은 실행 테스트나 브라우저 점검을 하지 않습니다.
- GitHub DB 파일 및 문서 원본은 수정하지 않았습니다. 서버 재시작 시 기존 FMEA 연결 컬럼을 추가하므로 실제 DB를 먼저 백업합니다. Oracle 배포는 사용자의 로컬 확인 뒤 별도로 진행합니다.

## 품질관리 검사·성적서 메뉴 선등록

품질관리의 검사/성적서 메뉴는 아래 순서로 기존 불량 처리 메뉴 위에 배치합니다.

1. 공정순회 검사: /quality/patrol-inspections
2. 입고 성적서: /quality/inbound-reports
3. 출하 성적서: /quality/outbound-reports

- 이번에는 사이드바·화면 제목·개발 예정 안내만 제공하며 작성/등록/저장 API나 테이블은 추가하지 않습니다.
- 기존 검사기준서·검사항목·불량 처리·LOT 데이터는 변경하지 않습니다.
- 향후 각 검사/성적서는 같은 item_id의 해당 검사유형 기준서 한 개와 연결하고 검사항목·규격을 가져옵니다. 실제 1:1 연결 및 기준 Revision/규격 보존 기능은 아직 구현하지 않았습니다.
- 기존 공통 안내 템플릿을 재사용하고 품질관리 문구만 페이지별로 표시합니다. 표준문서 안내 화면은 기존 문구를 유지합니다.
- 새 경로는 기존 사이드바 기반 계정 권한 목록에 자동 등록됩니다. 일반 사용자에게 권한을 자동 부여하지 않으며 직접 URL 접근도 READ/WRITE 권한을 확인합니다.
- 실행 테스트/브라우저 점검은 요청에 따라 수행하지 않았습니다. DB 변경과 Oracle 배포는 포함하지 않습니다.

## 개정번호의 구분과 세로 공정흐름도

- 품목 정보 관리에는 개정번호가 없습니다. 기존 item_master.revision 컬럼/값은 이력 보존용으로만 유지하며 입력/표시/자동 갱신에 사용하지 않습니다.
- 도면 관리의 revision_code는 도면 개정번호입니다. 현재 사용 적용이 품목마스터나 FMEA/공정흐름도 개정번호를 변경하지 않습니다.
- 공정흐름도/FMEA 및 향후 관리계획서·작업표준서·검사기준서·포장사양서는 해당 문서의 독립 개정번호를 사용합니다.
- 성적서는 앞으로 사용한 검사기준서 개정과 당시 기준을 참조/보존합니다. 아직 성적서 연동 기능은 없습니다.
- 공정흐름도는 기호 명칭 드롭다운으로 선택한 공통코드의 도형을 자동 표시하며 같은 공정 데이터를 세로 연결 흐름도로 출력/인쇄합니다.
- 입고검사 기준서의 기존 직접 수정/삭제 API를 이번 범위에서 임의 변경하지 않습니다. 이력 보존 정책 통합은 별도 설계/승인 대상입니다.

## 관리계획서 상단 양식

- 제목 가운데 정렬, 회사명/문서번호, 단계 체크박스(시작·선행양산·양산), 차종/품명/품번/상호기능팀원, 개정 이력 1~6행(NO·개정일자·개정사유·작성·검토·승인)을 제공합니다.
- 오른쪽에 제정일자와 작성/검토/승인 서명·날짜, 하단에 업체코드와 고객기술/고객 품질/기타 승인·일자(요구시)를 배치합니다. 차종·품명·품번은 선택한 완제품에서 표시하며 나머지 입력은 공란으로 시작합니다.
- ADMIN/WRITE는 상단 양식을 입력하고 READ는 비활성 입력란으로 조회합니다. 기존 메뉴 경로와 권한 키를 유지합니다.
- 상단 정보와 하단 관리항목을 초안으로 저장하고 독립 개정을 적용합니다. 서명란은 텍스트 입력이며 전자서명/결재 처리를 가장하지 않습니다. 상단 6행은 양식에 입력한 개정 참고 정보이며 실제 문서 개정 목록과 구분됩니다.
- 좁은 화면에서는 문서 전체를 가로 스크롤하며 인쇄는 A4 가로 방향의 상단 양식을 사용합니다.

- 상단은 사용자가 제시한 줄바꿈과 같은 7행 기준을 공유합니다. 1행은 단계/차종/개정표 제목/제정일자, 2행은 시작/품명/개정 1/결재 제목, 4행은 선행양산/품번/개정 3, 6행은 양산/상호기능팀원/개정 5, 7행은 개정 6/결재 날짜를 맞춥니다. 서명란은 3~6행에 걸쳐 배치합니다.

## 관리계획서 관리항목·저장·엑셀 불러오기

- 기존 FastAPI/Jinja2/SQLAlchemy를 사용합니다. 서버 시작 시 `control_plan_revisions` 테이블을 생성합니다. 기존 DB 파일이나 회사 원본 엑셀은 Git에 넣거나 수정하지 않습니다.
- 품목·문서번호별 독립 REV 번호, 초안 저장, 현재 사용 적용, 새 개정 등록과 이전 개정 조회를 제공합니다. 적용한 개정은 직접 수정할 수 없으며 새 개정 초안으로 내용을 복사합니다. 새 개정을 적용하면 이전 개정은 SUPERSEDED로 보존합니다. 문서 삭제 기능은 제공하지 않습니다.
- 공정흐름도의 번호·명칭·순서를 사용하고 한 공정 아래 관리항목을 여러 행으로 추가합니다. 설비명, 관리항목 NO/제품/공정, 특별특성, F/P·자동검사, 규격·확인방법·샘플 크기/주기·관리방안, 자재/생산/QC/기술 분담, 이상 조치와 비고를 입력합니다. 공정 상세란은 원자재명 등 추가 정보를 보존합니다.
- 적용 시 모든 공정에 관리항목과 규격·확인방법·관리방안·이상 조치를 요구합니다. 초안에는 미완성 입력을 저장할 수 있습니다.
- 문서 버전과 기준 흐름도 버전을 검사해 동시 변경/오래된 업로드 저장을 막습니다. 공정 스냅샷을 저장하므로 나중에 흐름도가 변경되어도 저장된 문서의 당시 순서는 바뀌지 않습니다. 변경된 흐름도로 다시 작성하려면 초안에서 기준을 선택합니다. 기준 변경은 확인 후 관리항목을 새로 작성합니다.
- 회사 파일 `D-110-008-005 관리계획서(310186-1)_REV7.xlsx`의 첫 시트, 11~13행 항목명 아래 A~AA 열을 읽습니다. 상단 기본 정보, 서명 이미지, 다른 시트와 AB 열 이후 인쇄 영역 밖의 메모는 가져오지 않습니다. 파일에 적힌 상단 품번을 사용하지 않으므로 업로드 전에 대상 완제품과 흐름도를 선택해야 합니다.
- 병합 셀은 항목별로 풀고 여러 줄 내용을 보존합니다. 같은 공정번호가 원자재별로 연속 반복되는 양식과 같은 NO 아래 다른 관리특성이 있는 양식을 지원합니다. 공정번호만으로 흐름도에 연결합니다. 공정명 내용은 필수가 아니며 비어 있으면 흐름도 명칭을 사용합니다. 엑셀에 적힌 명칭/원자재명은 상세 내용으로 보존하며 명칭 차이로 업로드를 차단하지 않습니다. 같은 번호가 흐름도에 여러 번 등장하면 잘못 연결하지 않도록 거부합니다.
